# 扩展手册：错误模型

本篇讲当前错误面如何编程式处理，以及计划中的统一错误体系。**现状先说清：dlz-goai 目前用 Go 惯用的 sentinel error + 包装，没有错误码体系**——那是 v0.3 的计划（见文末）。

## 处理原则

1. **优先 `errors.Is` 匹配 sentinel 错误**，不要解析错误字符串；
2. **区分两条失败通道**（这是本库的核心语义，见 [tool 手册](../使用手册/tool.md)）：
   - `tool.Result.IsError`：业务失败，**不是 Go error**——原因已回传模型自我纠正，调用方通常只需记录审计；
   - `error`：执行失败——agent 中止本轮，调用方需要决定重试、降级或报错；
3. **runtime 的持久化错误必须呈现**：fail-closed 意味着 `Run` 返回持久化失败时，运行已中止、状态已如实登记——吞掉它会让"界面显示成功、数据库停在 running"。

## Sentinel 错误清单

### agent 包

| 错误 | 含义 |
|---|---|
| `agent.ErrNoModel` | 未提供模型调用函数 |
| `agent.ErrNoTools` | 兼容保留。现行行为：空工具集退化为普通对话，不返回此错误 |
| `agent.ErrRunNotFound` | 审批决策目标运行不存在或已结束 |
| `agent.ErrApprovalNotPending` | 该调用当前不在等待审批（已决议或不存在） |
| `agent.ErrApprovalAborted` | 审批等待被中断（运行结束/取消） |

### runtime 包

| 错误 | 含义 | 典型处置 |
|---|---|---|
| `runtime.ErrRunNotFound` | 运行不存在 | 检查 runID；或已过期被清理 |
| `runtime.ErrRunTerminal` | 运行已成功结束，不能 Resume/重复发起 | 直接取 `Replay`/结果即可 |
| `runtime.ErrRunActive` | 运行进行中，不能重复发起或 Resume | 前端继续订阅 Stream 即可 |
| `runtime.ErrNoCheckpoint` | 无检查点（未配置存储或运行太早） | 确认 OpenRuntime/检查点 Store 配置 |

```go
_, err := rt.Resume(ctx, runID, cfg, model, nil)
switch {
case errors.Is(err, runtime.ErrRunActive):
	return // 已有实例在跑，前端继续订阅
case errors.Is(err, runtime.ErrRunTerminal):
	return // 已成功，无需处理
case errors.Is(err, runtime.ErrNoCheckpoint):
	// 配置问题，需要告警
default:
	// 真实执行/持久化失败：记录 errText（RunRecord.Error 已同步落库）
}
```

### tool 包

`ErrNoHandler`（handler 为 nil）、`ErrNotFound`（Registry 中不存在）、`ErrDuplicate`（同名注册）、`ErrInvalidArguments`（参数非法 JSON）、`ErrDenied`（策略禁止）——后三者通常不会到达你的代码：agent 会把它们转成**错误回执**（`EventToolError` + 模型可见的 tool 消息）交回模型自我纠正。

### mcp 包

`mcp.HTTPError`（带 `StatusCode`/`URL`/`Body`）；会话失效包装在 `errSessionInvalid` 后（当前未导出，通过 `Apply` 重建或重试恢复——正常使用不需要感知）。

## 错误信息的稳定性

- sentinel 错误的**文本是英文**且随版本可能微调——永远用 `errors.Is`，不要 `strings.Contains`；
- 包装错误（`fmt.Errorf("...: %w", err)`）保留链条，`errors.Is`/`errors.As` 可穿透；
- **模型可见的错误回执**（tool 消息里的 `error: ...` 前缀文本）不是 API——它是给模型读的自然语言，随提示词工程演进，不要用业务逻辑解析它。

## 计划中：统一 Error 码体系（v0.3）

来自[嵌入式集成架构设计](../embedded-integration-design.md) §16，预计随最小 Client 门面一起落地：

```go
type Error struct {
	Code      string // 机器可读，见下表
	Message   string // 人类可读
	Retryable bool   // 调用方可安全重试
	Cause     error  // 包装链
}
```

规划的错误码：`invalid_config` `component_not_found` `component_conflict` `model_unavailable` `tool_not_found` `tool_invalid_arguments` `tool_execution_failed` `approval_rejected` `run_not_found` `run_not_resumable` `run_canceled` `persistence_failed` `context_limit_exceeded`。

落地后承诺：现有 sentinel 错误用 `errors.Is` 保持可匹配（旧代码不破坏）；`Error.Code` 是新代码的推荐判定入口；敏感信息（API key、URL 内嵌凭据）不出现在 `Message` 与日志中。

在此之前，跨版本的错误处理建议集中在应用内一个适配函数里（sentinel → 应用错误码），升级时只改一处。
