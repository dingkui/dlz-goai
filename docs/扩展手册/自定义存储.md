# 扩展手册：自定义存储

runtime 与 rag 的存储全部走接口注入。内置实现（memory / sqlite）之外，你可以接入 PostgreSQL、Redis、专用向量库或公司内部的存储中间件。实现前请通读本文的契约要求——runtime 的恢复语义建立在它们之上。

## runtime 三 Store

```go
type RunStore interface {
	Create(ctx context.Context, record RunRecord) error
	Update(ctx context.Context, record RunRecord) error // 全量覆盖
	Get(ctx context.Context, runID string) (RunRecord, error)
	List(ctx context.Context, statuses ...Status) ([]RunRecord, error)
}
type EventStore interface {
	Append(ctx context.Context, runID string, events ...agent.Event) error // append-only
	List(ctx context.Context, runID string) ([]agent.Event, error)
}
type CheckpointStore interface {
	Save(ctx context.Context, cp Checkpoint) error // 同 RunID 覆盖
	Load(ctx context.Context, runID string) (Checkpoint, error)
}
```

### 契约要求（违反会破坏恢复语义）

| 接口 | 硬性契约 |
|---|---|
| `RunStore.Create` | ID 重复应报错（防止重复发起被静默接受） |
| `RunStore.Update` | **全量覆盖**；ID 不存在返回 `runtime.ErrRunNotFound`；调用方先 Get 再改字段 |
| `EventStore.Append` | **append-only、顺序即到达顺序**；不重排不去重；运行不存在时 `List` 返回空切片而非错误 |
| `CheckpointStore.Save` | 同 RunID **覆盖**旧值（runtime 只需最新可恢复点；保留历史是实现方的自由） |
| `CheckpointStore.Load` | 无检查点返回 `runtime.ErrNoCheckpoint` |

**错误必须返回，不要吞**。runtime 是 fail-closed 语义：持久化失败会中止运行并传给调用方——你吞掉的每一个错误，都会变成"恢复时静默重放"的生产事故。

### 序列化注意

- `agent.Event` / `RunRecord` / `Checkpoint` 的 JSON tag 是公共契约（`tool`/`message` 结构体的字段也是）——用 JSON 落库时不要改 tag；
- `Checkpoint.Options` 可能为 nil；`Message.Images` 是 base64 data URI 数组，可能很大（ModelBox 踩过 27MB 单会话的坑），评估存储预算；
- `Checkpoint.Messages` 里 `Citations` 字段带 `json:"-"`，**不序列化**——引用在事件与 `Result` 里流转，恢复时从续跑点重新累积。

### 实现参考

`storage/sqlite` 的三个实现是最完整的参照（表结构、错误处理、`ErrRunNotFound` 语义）；`runtime/memory` 是最小实现。两份实现的测试（含故障注入）就是你的契约测试模板。

## rag 存储接口

```go
type VectorStore interface {
	Store(ctx context.Context, docID string, chunks []Chunk, vectors [][]float32) error // 同 DocID 覆盖
	Remove(ctx context.Context, docID string) error
	Search(ctx context.Context, query []float32, topK int, filter Filter) ([]SearchResult, error) // Score 降序
}
type FullTextStore interface { // 可选通道：与向量通道经 RRF 融合
	Index(ctx context.Context, docID string, chunks []Chunk) error
	Remove(ctx context.Context, docID string) error
	Search(ctx context.Context, query string, topK int, filter Filter) ([]SearchResult, error)
}
```

要点：

- `Store` 的 chunks 与 vectors **等长一一对应**（sqlite 实现会校验并在单事务内提交——同文档部分写入会让检索出现半篇幽灵内容）；
- `Search` 结果按 `Score` 降序；`filter` 返回 false 的候选不进入结果（在存储层过滤比返回后再过滤省得多）；
- `SearchResult.Citation` 可由实现方填充（从 Chunk 推导），下游 `rag.NewTool` 会自动聚合引用；
- 向量序列化可直接用 `rag.EncodeVec`/`DecodeVec`（LittleEndian float32）；
- 大规模场景：暴力余弦在数万 chunk 内可用，之上考虑 HNSW 等索引——接口不变，只换实现。

`Embedder`（`Embed`/`EmbedBatch`）与 `Reranker`（`Rerank`）同样可自定义；Reranker 实现建议参考的容错设计：先探一条（服务不可达整批放弃）、并发限流、单条失败原序追加、整批失败原样返回——任何失败只影响排序不丢结果。

## 配置接入建议

存储实现由应用在启动时装配（所有权归应用——`Client`/`Runtime` 不会替你关闭外部资源）：

```go
rt := runtime.New(runtime.Options{
	Runs:   pg.NewRunStore(pool),   // 你的实现
	Events: pg.NewEventStore(pool),
	// Checkpoints 不配置 = 跳过检查点能力（Resume 将不可用）
})
```

只想持久化事件、不要检查点？Store 按接口独立注入，缺哪个就少哪项能力——组合是你的自由，runtime 不强制三件套齐全。
