# 扩展手册：事件与流式集成

agent 与 runtime 的一切行为都通过 `agent.Event` 对外暴露。本篇讲事件模型的完整语义，以及把事件流接到前端（SSE/WebSocket）的参考实现——模式提炼自 ModelBox 的生产实践。

## Event 模型

```go
type Event struct {
	Type       string // 见下表
	Seq        int64  // runtime 分配，单运行内单调递增（裸 agent 为 0）
	RunID      string
	Step       int
	Content    string           // model_delta 的正文增量 / final 的最终回答
	CallID     string           // 工具调用标识（Proposed/Approval/Started/Result 关联键）
	ToolName   string           // 含命名空间（MCP 工具为 mcp__{server}__{name}）
	SourceID   string           // 来源标注（Sourced 工具）
	SourceName string
	Arguments  map[string]any   // 模型给出的调用参数
	Result     string           // 工具回执文本
	Error      string           // tool_error / run_error 的原因
	Approved   *bool            // approval_required 第二次发出时标注决议结果
	Citations  []tool.Citation  // 引用
	Finish     string           // final 的结束原因（stop / max_steps）
	PromptTokens, EvalTokens int // 用量（Ollama 提供，OpenAI 兼容通常 0）
	EvalMs, TotalMs          int64
}
```

| 事件 | 时机 | 消费建议 |
|---|---|---|
| `run_start` | 运行开始 | UI 显示"开始处理" |
| `model_delta` | 正文增量 | 流式渲染 |
| `tool_proposed` | 模型请求调用（未校验策略） | 显示"准备调用 X" |
| `approval_required` | 等待审批；决议后**再发一次**（Approved 非 nil） | 渲染确认卡片 → 决议后更新状态 |
| `tool_started` | 工具开始执行 | 显示执行中 |
| `tool_result` / `tool_error` | 工具返回 / 业务失败 | 展示结果卡片（error 也要展示——它是模型自我纠正链路的一部分） |
| `step_done` | 一步结束 | 步骤分组 |
| `final` | 运行结束 | 收尾渲染 |
| `run_resumed` / `run_done` / `run_error` | runtime 层：续跑 / 成功 / 失败 | UI 状态机切换 |

## 事件与持久化的一致性

用 runtime 时：**emit 收到的每个事件都已落库且带 Seq**。这给了一个重要保证——任何时刻消费者都可以用 `Replay`/`Stream` 重建与实时完全一致的序列。裸 `agent.Run` 没有这个保证（事件不落库、无 Seq），要做流式集成请从 runtime 起步。

## SSE 集成参考（ModelBox 模式）

```go
func (h *Handler) Chat(w http.ResponseWriter, r *http.Request) {
	flusher := w.(http.Flusher)
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	var mu sync.Mutex                       // ① 写互斥：业务发送与心跳并发写
	write := func(event, data string) {
		mu.Lock(); defer mu.Unlock()
		fmt.Fprintf(w, "event: %s\ndata: %s\n\n", event, data)
		flusher.Flush()
	}
	stop := make(chan struct{})
	defer close(stop)
	go func() {                              // ② 心跳：审批等待时连接可能长时间静默
		t := time.NewTicker(15 * time.Second)
		defer t.Stop()
		for {
			select {
			case <-stop: return
			case <-t.C:
				mu.Lock(); fmt.Fprint(w, ": ping\n\n"); mu.Unlock(); flusher.Flush()
			}
		}
	}()

	runID := rt.BeginRun()
	write("run", runID)
	_, err := rt.Run(appCtx, msgs, nil, agent.Config{RunID: runID, Tools: h.tools}, h.callModel,
		func(e agent.Event) {              // ③ 事件转发 + 增量落库
			b, _ := json.Marshal(e)
			write(e.Type, string(b))
		})
	_ = err
}
```

三个关键点：

1. **写互斥**：心跳 goroutine 与事件转发并发写 `ResponseWriter`，必须加锁；
2. **心跳**：代理/网关会掐断静默连接，15s 一行 `: ping`（注释行，旧客户端天然兼容）；
3. **事件转发与持久化解耦给 runtime**：emit 回调里只做转发，落库由 runtime 完成——不要自己再抄一份。

### 审批走独立端点，不走 SSE

`approval_required` 事件到达 → 前端渲染确认卡片（展示 `ToolName`/`Arguments`/来源）→ 用户点击 → **POST /approve**（携带 runID/callID/approved）→ `rt.Approve(...)` 解除运行阻塞 → 决议结果经第二次 `approval_required` 事件（`Approved` 字段）广播给所有订阅者。SSE 连接断开不影响审批等待。

### 断线重连：afterSeq 续传

客户端记住最后收到的 `Seq`，重连时 `Stream(ctx, runID, afterSeq, emit)`——先补齐缺口再接实时，交付序列与 Replay 一致（连续、含终态）。**运行结束不等于事件流消失**：只要 Store 在，任意时刻可完整回放。

### 前端事件模型

最小可用集合：`model_delta`（流式文本）、`tool_proposed`/`tool_started`/`tool_result`（执行卡片，按 CallID 关联）、`approval_required`（确认卡片）、`run_done`/`run_error`（终态）。按 `Step` 分组、按 `CallID` 关联调用与结果，即可渲染出完整的执行轨迹。

## WebSocket / 其他协议

事件是纯 JSON 可序列化结构，协议无关。要点只有两条：**慢消费者要有背压策略**（runtime 的实时通道缓冲 256、满则丢弃——必须配 Stream 式缺口补读；自定义通道可自行实现阻塞背压）；**终态事件必须可达**（丢终态 = 消费者永久等待）。
